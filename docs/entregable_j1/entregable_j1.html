CREATE TABLE IF NOT EXISTS products (
  id          SERIAL PRIMARY KEY,
  name        VARCHAR(255)   NOT NULL CHECK (length(trim(name)) > 0),
  price       NUMERIC(10, 2) NOT NULL CHECK (price > 0),
  image       VARCHAR(500)   NOT NULL,
  created_at  TIMESTAMP      NOT NULL DEFAULT CURRENT_TIMESTAMP

backend/src/controllers/productController.js (la ruta en productRoutes.js solo hace router.get("/", getProducts))

export const getProducts = async (req, res) => {
  try {
    const products = await sql`
      SELECT id, name, price, image, created_at
      FROM products ORDER BY created_at DESC`;
    res.status(200).json({ success: true, data: products });
  } catch (error) {
    res.status(500).json({ success: false, message: "Error interno del servidor" });
  }
};

backend/src/app.js

1.3 Cliente React: estado compartido con Zustand y Axios

frontend/src/store/useProductStore.js

export const useProductStore = create((set) => ({
  products: [], loading: false, error: null,
  fetchProducts: async () => {
    set({ loading: true, error: null });
    try {
      const res = await api.get("/api/products");
      set({ products: res.data.data });        // campo "data" del contrato
    } catch (err) {
      set({ products: [], error: "No se pudo cargar el catálogo." });
    } finally { set({ loading: false }); }
  },
}));

3. Explicación del flujo

El recorrido de una consulta atraviesa las tres capas del stack. Cada componente tiene una sola responsabilidad:

ReactVista + Zustand
→
AxiosHTTP GET
→
ExpressRuta + controlador
→
PostgreSQLNeon
1Montaje de la vista. Al cargar HomePage, el useEffect llama a fetchProducts() del store y se activa loading.
2Petición HTTP. Axios envía GET /api/products; en desarrollo el proxy de Vite la reenvía a localhost:3000.
3Middlewares. Express aplica cors (origen permitido), helmet (encabezados) y morgan (bitácora).
4Ruta → controlador. productRoutes delega en getProducts, que concentra la lógica de la operación.
5Consulta SQL. El cliente de Neon ejecuta el SELECT sobre products en PostgreSQL y devuelve las filas.
6Respuesta JSON. El controlador responde 200 { success, data }. Si la consulta falla responde 500.
7Actualización del estado. Zustand guarda res.data.data en products y desactiva loading.
8Render. React dibuja una ProductCard por producto o, si la lista está vacía, el mensaje de estado vacío.

Decisiones de diseño

DecisiónMotivo
Campo data siempre presenteEl cliente lee la misma ruta del JSON con o sin productos; una lista vacía no es un error (200, no 404).
Rutas separadas de controladoresLas rutas solo enrutan; la lógica queda en un lugar que se puede probar y reutilizar.
app.js separado de server.jsSupertest importa la aplicación sin abrir un puerto real.
Consultas con plantilla sql`...`Los valores viajan como parámetros: protege contra inyección SQL desde HU02 en adelante.
.env fuera de GitLa cadena de Neon contiene credenciales; se versiona solo .env.example.
Estado en ZustandEl catálogo se compartirá con el formulario de alta (HU02) y la página de edición (HU03).

Cómo reproducir la demostración

  1. Ejecutar backend/db/schema.sql y backend/db/seed.sql en el SQL Editor de Neon.
  2. Copiar backend/.env.example a backend/.env y colocar la DATABASE_URL.
  3. cd backend && npm install && npm run dev (API en el puerto 3000).
  4. cd frontend && npm install && npm run dev (React en el puerto 5173).
  5. Para el estado vacío, ejecutar backend/db/empty.sql y recargar la vista.
  6. Pruebas automatizadas: cd backend && npm test.
