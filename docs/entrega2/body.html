2. Validación con Zod y DTO

El DTO (objeto de transferencia de datos) define exactamente qué campos y tipos cruzan la interfaz HTTP. Se valida en Express antes de llegar al controlador: si algo no cumple, la API responde 400 y nunca se ejecuta SQL.

backend/src/dto/productDto.js

export const productInputSchema = z.object({
  name: z.string().trim()                          // quita espacios al inicio y al final
    .min(1, "El nombre no puede estar vacío").max(255),
  price: z.preprocess(toNumber, z.number()           // acepta 650 o "650", rechaza "", null, "abc"
    .finite().positive("El precio debe ser mayor que 0")),
  image: z.string().trim().url("La imagen debe ser una URL válida").max(500)
    .refine((u) => /^https?:\/\//i.test(u), "La URL debe iniciar con http:// o https://"),
}).strict();                                       // cualquier otro campo (p. ej. id) → 400

backend/src/middleware/validate.js

export const validate = (schema, source = "body") => (req, res, next) => {
  const result = schema.safeParse(req[source] ?? {});
  if (!result.success) {
    // { "price": "El precio debe ser mayor que 0", ... }  un mensaje por campo
    return res.status(400).json({ success: false, message: "Datos inválidos", errors });
  }
  req.validated = { ...req.validated, [source]: result.data };   // datos ya limpios
  next();
};

backend/src/routes/productRoutes.js

router.post("/", validate(productInputSchema), createProduct);
router.get("/:id", validate(idParamSchema, "params"), getProduct);
router.put("/:id", validate(idParamSchema, "params"), validate(productInputSchema), updateProduct);
router.delete("/:id", validate(idParamSchema, "params"), deleteProduct);

Defensa en dos capas

CapaQué protege
Zod (Express)Tipos, nombre vacío, precio ≤ 0, URL inválida, campos extra, id no numérico. Da mensajes claros por campo.
PostgreSQLCHECK (price > 0) y CHECK (length(trim(name)) > 0) del esquema: última barrera si algo saltara la API.
Consultas parametrizadasLos valores viajan como $1, $2… en sql`...`; las pruebas verifican que nunca se concatenan.

El formulario de React usa noValidate a propósito: la fuente de verdad es la API y la vista muestra sus mensajes debajo de cada campo (Fig. 1).

Rutina aplicada en cada historia

  1. Tarjeta en En desarrollo y rama feature/HUxx-… desde la anterior.
  2. Commits vinculados a la historia (feat(HU02): …) con sus pruebas.
  3. Pull request con criterios de aceptación y Closes #n; tarjeta a En revisión.
  4. Otro integrante revisa y aprueba en GitHub.
  5. Se integra en main, se etiqueta u4-jN y la tarjeta pasa sola a Liberada.

8. Resultado y siguiente paso

Resultado

El catálogo ya tiene el CRUD completo: consultar, dar de alta, editar y eliminar, con los datos en PostgreSQL (Neon). La API rechaza la entrada inválida con mensajes por campo antes de tocar la base, distingue 400, 404 y 500, y la vista de React refleja cada caso sin perder el último dato confirmado. Todos los criterios de HU02, HU03 y HU04 se comprobaron de forma manual (React y Postman) y automatizada (37 pruebas).

Cómo reproducir

  1. Preparar la base: node db/run-sql.js db/schema.sql y db/seed.sql (desde backend/).
  2. cd backend && npm install && npm run dev · cd frontend && npm install && npm run dev.
  3. En http://localhost:5173: Agregar producto, Editar y Eliminar en cada tarjeta.
  4. Pruebas: cd backend && npm test.
